## Decisions log (with why)

- **2026-07-23 (M9 Stream B)** — `ProviderManager`'s M2-M8 primary/fallback/cooldown state machine was **deleted outright, not left dormant**, when OmniRoute became the sole LLM backend. Considered keeping the multi-provider machinery and just constructing it with a single-entry dict (smaller diff, `_other_configured()` would just always return `None`) — rejected: dead branches that can never execute under the new architecture are exactly the kind of speculative flexibility docs/04 already argues against elsewhere, and `set_active`/`configured_names`/hot-swap-between-providers are concepts with literally nothing to apply to anymore. The owner explicitly chose no-cloud-fallback (single point of failure accepted for a local dev/classroom app) — that decision is *why* the simplification is safe, not just a style preference. Also: OmniRoute's own public docs don't document a specific model id with confirmed tool-calling support (unlike OpenRouter's catalog at M8) — rather than guess a vendor model string that might not even be a valid OmniRoute route, `auto/coding` (OmniRoute's own named "quality-first" combo) was picked as an explicit, flagged-⚠️-unverified placeholder, with the owner told directly they must confirm/replace it via their own running dashboard. Never invent a specific model/config value that can't be verified from available sources — flag it instead.
- **2026-07-23 (M9 Stream A)** — TTS moved from in-process `pocket-tts` (M4 decision, entry below) to a separately-run local microservice (`takada-tts-service`), per explicit owner direction: the owner already runs the service (Docker or `uvicorn`) and wanted Nova to stop owning the PyTorch runtime itself. This is a full supersession of the M4 TD-6 rewrite below, not an addition — `pocket_tts.py` was deleted, not kept alongside. Two reasons beyond "owner already has the service": (1) it structurally eliminates the dtype-mismatch bug class the WDM-KS fix branch (`fix/wdm-ks-device-validation`, same day) was patching symptoms of — there's no `torch.Tensor` on Nova's side anymore, the service emits PCM16 directly; (2) it removes PyTorch from Nova's own packaged footprint (the single biggest line in TD-6's M4 dependency-budget revision, ≈1.2–2 GB). The response contract (`POST /v1/synthesize` → streamed WAV, `audio/wav`) was confirmed by reading `takada-tts-service`'s own FastAPI route + `wav.py` source directly (`C:\Projects\takada-tts-service\app\main.py`/`wav.py`), not guessed or inferred from a README — the service streams an *unbounded* WAV (44-byte header + `writer.setnframes(1_000_000_000)` + a patched no-op `_patchheader`, the same trick pocket-tts's own `StreamingWAVWriter` uses), which is why the client parses the fixed-size header directly instead of using stdlib `wave` to read the response (that module expects a seekable, correctly-sized file). `ProviderManager`-equivalent fallback logic wasn't needed here — `pyttsx3` was already the fallback engine and needed zero changes, since `RemoteTTSEngine` raises the same `SpeechError` shape `PocketTTSEngine` did.
- **2026-07-23 (file_opener)** — `main` is **not** the integration branch for this repo, despite being git's default: it's still the bare initial scaffold (`git log` shows only 2 commits — repo init + LICENSE). `development` is where M1–M6 actually merged (PRs #5/#6 both targeted it) and where M8/this fix branch from. A new feature branch was mistakenly cut from `main` first, discovered `src/nova/tools/` was empty there, corrected by deleting it and re-branching from `development`. **Always branch from `development`, never `main`, unless told otherwise.** Separately: `file_opener` was scoped as a new sibling tool to `file_search` (not a mode bolted onto `file_search`, and not a parameter added to `app_launcher`) — `file_search`'s spec explicitly says "read-only by construction" (Sensitive: No, by design intent, not just incidentally), and `app_launcher`'s whole purpose is resolving an app *name*, a different concern from opening a known *path*. Keeping them separate also avoided touching `app_launcher`'s frozen `app_name`-only params (would've forced an unnecessary schema-drift golden update on an unrelated tool).
- **2026-07-12 (M6)** — First-run welcome (T-603) implemented as Settings auto-display + welcome banner, not a separate welcome screen/dialog. Why: SettingsView already guides key entry (docs/09 §2, T-209); re-routing first-run through it leverages existing wiring instead of building parallel UI. The banner + banner visibility property were sufficient without restructuring MainWindow's stacked widget. Release script (T-601) uses `uv sync --frozen` and a clean `.venv.build` per-build, not in-place deps — keeps release artifacts reproducible.

Not a product bug — scratchpad-only script — but worth a Gotchas entry since it'll bite the same way in any future ad-hoc offscreen driver.
- **2026-07-10 (M4)** — Primary TTS swapped `edge-tts` → `pocket-tts` (Kyutai Labs) **per explicit owner direction mid-build**, not an agent-initiated substitution. Why: a local, CPU-only neural voice removes edge-tts's unofficial-Microsoft-endpoint fragility (docs/04 TD-6's own ⚠️) entirely rather than mitigating it, and needs no network per-utterance. Real, accepted cost: `pocket-tts` pulls in PyTorch 2.5+ — pinned to the CPU-only wheel index (`download.pytorch.org/whl/cpu` via `[tool.uv.sources]`) to avoid the much larger CUDA-bundled default; measured real footprint on this dev machine: `torch` ≈ 477 MB alone, whole dev venv ≈ 1.53 GB (up from docs/04's original ≈ 300–400 MB estimate for the whole app). `TD-7`'s original rejection of `silero-vad` ("avoid pulling in torch/ONNX for VAD") is now a moot premise since torch is in the tree anyway for TTS — documented as a cross-reference note in TD-7, VAD left unchanged (still nothing to gain from switching). Two more real findings from hands-on testing (not assumptions): (1) `TTSModel.load_model()` took 30–100s even with cached weights on this machine — `SpeechService.warm_up_tts()` was added specifically so this cost lands at app startup (background thread) rather than on a user's first spoken reply; (2) voice selection must use pocket-tts's built-in catalog names (`cosette`, `alba`, …) — an `hf://` voice-cloning URL (the obvious-looking API for "pick a voice") 404s/requires gated Hugging Face access, confirmed by an actual failed call during testing, not by reading docs alone. ## Gotchas discovered

- **M6**: `nova.ui.theme` does not export `button_style()` function — attempting to call it raises `AttributeError`. Buttons use the global QSS stylesheet instead; use `setStyleSheet()` only for per-widget overrides (color text, background, etc.), not for structural styling.
- `QAbstractButton.click()` (incl. `QPushButton`) is a no-op — does not emit `clicked` — when the button is disabled. Useful for testing a disabled-during-request Send button "for real" without needing `qtbot.mouseClick`; but if a test wants to isolate a *different* guard (e.g. an internal `_awaiting_reply` flag) independent of Qt's own disabled-widget suppression, re-enable the widget first so the click actually reaches the handler.
- pytest-qt 4.5.0's `waitSignal` context manager throws (`AttributeError: 'MultiSignalBlocker' object has no attribute 'check_params_callback'`) if the watched signal fires more than once inside the `with` block — use `qtbot.wait_until(predicate)` instead for signals that may emit rapidly/repeatedly (e.g. EventBus bursts from a worker thread).
- `QWidget.isVisible()` reflects the *whole ancestor chain*, not just the widget's own flag — a widget tree that's never been `.show()`n reports `isVisible() == False` even right after `setVisible(True)`. Cost time in a PulseRing repaint-count test and a StageChip expand/collapse test; fix is `.show()` (+ `qapp.processEvents()`) before asserting visibility/paint counts, or use `.grab()` which forces a synchronous render regardless of shown state.
- `Qt.WidgetAttribute.WA_TransparentForMouseEvents`, applied recursively to a composite row's children, reliably forwards clicks to one outer handler — used so `StageChip`'s whole row (icon/text/status labels) click-through to the outer widget's single `mousePressEvent`. Confirmed via a real `qtbot.mouseClick` dispatch, not just a direct method-call test.
- Variable fonts (`Inter[opsz,wght].ttf`, `JetBrainsMono[wght].ttf` from the google/fonts repo) load fine via `QFontDatabase.addApplicationFont`, and `QFont.setWeight()` correctly selects the right instance — no need to source separate static per-weight files.
- Lucide renamed `alert-triangle` → `triangle-alert` and `shield-question` → `shield-question-mark` upstream at some point (old names 404 on raw.githubusercontent.com). Fetched under the new names; saved locally as `assets/icons/alert-triangle.svg` / `shield-question.svg` to match the names docs/05 §5 actually specifies.
- Qt's SVG renderer does not resolve Lucide's `stroke="currentColor"` — icons are tinted by rendering to a transparent QPixmap then filling with `CompositionMode_SourceIn` (`nova.ui.theme.load_icon`), not by editing the SVG source.
- `QTimer.singleShot()` called before a `QApplication` exists silently never fires (no error) — see M5 decisions log entry above. Only schedule driver/test timers after the app is constructed (e.g. from inside a patched `show()`, or after `QApplication(sys.argv)` in a script).
- Newly-inserted child widgets in an already-shown `QVBoxLayout` don't paint on the very next `.grab()` — Qt defers the actual layout pass to the next event-loop iteration (a posted `LayoutRequest`), so a synchronous `set_facts([...]); widget.grab()` with no event-loop turn in between grabs a still-zero-sized child. Call `QApplication.instance().processEvents()` between the mutation and the `.grab()` in any offscreen driver/test that adds widgets and immediately screenshots.
